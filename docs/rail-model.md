# 轨道美术加载

美术资源直接放进 `assets/vastseatrain/models/block/rail/`，程序**只读不写**。保护规则见 [`docs/art-assets-policy.md`](docs/art-assets-policy.md)。

## 目录划分

```text
assets/vastseatrain/models/block/
  rail/                     ← 美术目录，程序禁止写入
    test.obj
    test.mtl
    gravel.png / concrete_silver.png / rail_sleeper_side.png /
    rail_sleeper_top.png / rail_fastener.png
  rail_core.json            ← 程序配置：加载器、贴图映射、摆放
  rail_mtl.mtl              ← 材质覆盖文件（程序侧）
```

## 为什么需要自定义加载器 `vastseatrain:rail_obj`

`forge:obj` 在 1.20.1 上有两个坑，都会让美术模型在游戏里“看起来不对”。程序侧全部在烘焙阶段处理，**美术文件一个字节都不用改**。

### 1. UV 越界 → 花屏（“只有钢轨材质正确”的真因）

实测各分组的 UV 范围：

| 分组 | UV 范围 | 是否在 0..1 |
| --- | --- | --- |
| `rail_left_rail` / `rail_right_rail` | u 0..1，v 0.405..0.595 | ✅ |
| `rail_full_ballast` | u −1.641..2.339，v −1.641..2.641 | ❌ |
| `rail_center_sleeper` | u −0.780..1.780，v −0.780..1.780 | ❌ |
| `rail_center_fastener` | u −1.285..2.285，v −1.299..2.299 | ❌ |

美术是按“1 个单位 = 1 张贴图”的世界投影导出的（道砟实测 `u = z + 0.5`、`v = y + 0.78`），靠渲染器的**重复采样**。Minecraft 的方块贴图是一整张图集，采样越界就会取到图集里相邻的其他方块贴图——这就是游戏里出现木板、石砖、花等原版图案的原因。钢轨 UV 恰好整个落在 0..1，所以只有钢轨正常。

程序侧解决：`RailObjGeometry` 把每个三角面按 UV 整数格**裁剪切块**，每块独立映射一整张贴图。等价于渲染器的 UV 重复采样，形状零损失。

### 2. 平移被朝向旋转 → 只有朝北时偏移正确

`forge:obj` 的做法是 `modelTransform.getRotation().compose(rootTransform)`，即 JSON 的 `transform.translation` 被放在方块朝向旋转**之内**。推导结果是：

```text
pos = Rot( p + t − (1,1,1) ) + (1,1,1)
```

朝北（Rot=I）时 `pos = p + t` 恰好正确，一旦朝向变化，0.5 的补偿会被转到别的轴上，轨道立刻偏半格到一格。

本加载器改为：

```text
pos = Rot(朝向) · p + translation
```

平移在旋转之后叠加，四个朝向完全一致。`translation` 的含义就是“模型原点落在方块局部坐标的哪个位置”。

## 模型数据与摆放

`test.obj` 实测包围盒：X −0.801..0.801（长度轴）、Y −1.000..0.750（轨面 0.750）、Z −2.141..2.141（宽度轴）。

```json
"transform": { "translation": [0.5, 0.5, 0.5] }
```

`[0.5, 0.5, 0.5]` = 模型原点落在方块中心。道砟底（Y −1.000）因此落到方块下表面，轨面（0.750）在方块顶面上方 0.25 格，与美术在 Outliner 里看到的比例一致。

## 朝向对照

模型长度轴是 X、前进方向 −X。`blockstates/rail.json` 用 `y` 旋转把长度轴对齐到前进方向：

| facing | y | 效果 |
| --- | --- | --- |
| north | 90 | 长度轴转到 Z（南北） |
| east | 180 | 长度轴保持 X（东西） |
| south | 270 | 长度轴转到 Z（南北） |
| west | 0 | 长度轴保持 X（东西） |

（旧配置是 0 / 270 / 180 / 90，整体差 90°，这也是“旋转偏移 90 度”的原因。）

## 占位、碰撞与铺设

- **每段 1 个方块**：蓝图沿玩家视线方向逐格前推，每格只放一个 `rail` 方块，**不再并排铺 3 条轨道**。
- **模型自身横跨 3 格宽**（Z 方向 4.28 格，略微越界属正常观感）。
- **碰撞箱 3 格宽 × 1 格长 × 1/16 高**：由 `RailBlock#getCollisionShape` 按朝向给出越界形状（南北向沿 X 铺开、东西向沿 Z 铺开）。
- **整段破坏**：一次铺设登记为一段（`TrackSegments`），破坏任意一格即整段移除。

## 90° 弯道

弯道**不改动美术模型**，也不生成新的模型文件，只把同一份 `test.obj` 沿弧线重复摆放。

### 排布方式（与 Immersive Railroading 相同）

每一份都是**完整的、未裁剪的**模型，只做平移 + 绕 Y 轴旋转（转到该处的切线方向）：

```text
        [====][====][====]  ← 每份 = 一份完整模型，各自转到切线方向
```

- 内侧条带自然重叠、外侧由模型自身 3 格宽的道床盖住，钢轨不会被切断；
- 第 `k` 份模型的原点放在弧长 `k` 处（`k = 0 .. ceil(弧长)-1`），相邻两份模型中心线首尾相接、接缝处顶点一致，不会闪面；
- **这条弯道覆盖到的每一格都有一个方块**：先沿弧线每 5 cm 采样，把采样点向两侧扩到道床半宽（1.6 格），得到全部被覆盖的格子；格子比条带多出来的部分，补一份“离本格最近的那段弧”。如果只按弧线经过的格子放方块，相邻格会经常只在对角相接，轨道就会看起来断开。

### 半径与轨距

- 圆心的定义：入口格中心 + `R` × 弯心方向。所以 `s = 0` 就是入口格中心、切线就是入口方向，与直道严丝合缝。
- 轨距半宽 `RailCurve.HALF_GAUGE = 0.645` 格（由美术模型钢轨位置 `|x| ≈ 0.5..0.79` 实测），内轨半径 `R − 0.645`、外轨半径 `R + 0.645`。
- 半径范围在 `VTConfig` 里：`minRadius 10` / `maxRadius 1024`，超过 `warnRadius 256` 时界面会提示方块数。

### 每格的数据

`rail_curve` 方块每格带一个 `RailCurveBlockEntity`，保存这些数：

| 字段 | 含义 |
| --- | --- |
| `Angle` | 绕 Y 轴旋转角（弧度），把模型局部 −X 转到该处切线 |
| `OriginX` / `OriginZ` | 模型原点在方块局部坐标里的位置（0..1） |
| `Radial` | 径向微调（格，负值朝圆心）。整条弯共用同一个值，只在入口 2 格内从 0 过渡过来 |
| `Radius` / `Left` | 参考信息，供提示与调试，不参与渲染 |

客户端 `RailCurveBakedModel` 在**区块烘焙时**（不是逐帧）读取方块实体，按下面的公式生成顶点，结果缓存进区块网格，所以每格绘制成本与直道相同：

```text
a  = p.x − originX + radial·cosθ     比重心旋转
b  = p.z − originZ + radial·sinθ
x' = cosθ·p.x − sinθ·p.z + originX + radial·cosθ
y' = p.y + 0.5
z' = sinθ·p.x + cosθ·p.z + originZ + radial·sinθ
```

（`originX/originZ` 是该格模型原点在方块局部坐标里的位置，`θ` 是绕 Y 轴旋转角。）

### 为什么要有 `Radial`

模型里的两行钢轨是**直的**，位于 `x ∈ [−0.501, 0.501]`、到段中心线约 `±0.645`。翻成弯道后：

- 如果半径按**模型中心线** `R` 算，内侧钢轨（半径 `R − 0.645`）必须弯得比模型更急，
  在 `L = 0.8` 的条带里累积的弦高误差约 `L²/(8(R−0.645))`，R = 10 时约 1.4 cm。
- 只要把整条弯的模型中心线放到半径 `R_real = R + 0.645/R` 的圆上，内外两根钢轨就**同时**正好落在 `R ± 0.645` 的圆弧上，残余误差在毫米级。

所以每个格子的模型原点朝圆心方向挪 `0.645 / R`。这个值对整条弯是**常量**，相邻格不会错位；入口那一份保持不动（与直道完全一致），随后 2 格内线性过渡。

模型顶点本身一个都没有改，只有整套模型被刚性旋转和平移，不存在“模型被压扁/拉断”的失真。

> 为什么在 `getModelData` 里直接读方块实体、而不走 `ModelDataManager`：后者需要方块实体主动调用刷新，存档重载或客户端刚收到方块数据时容易晚一拍，会让轨道先渲染成直道再跳变。
